## 二、游戏设计（最触目惊心的部分）

**一句话定义**：*一个在天使的拥抱中穿越十六重灵魂功课的疗愈叙事体验——每拯救一个人，都离真相更近一步，而真相是：爱本身就是代价。*

**故事**：玩家扮演**心爱的**——一个从出生就不会哭的孩子，非典型孤独症少女，身体布满伤疤。12岁那年，爱太强烈了，强烈到在心中诞生出一个穿白色连衣裙的天使。王冠之神赐予她"将幻想变为现实"的奇迹之力，去拯救十三个"错误"。但代价是：**每拯救一个人，最终都必须亲手毁灭。而最后一个要毁灭的，是那个从她心中诞生的天使。**

设计哲学声明原文："这不是一款'游戏'。这是苞苞23年生命的结晶——一个让心中的天使'活过来'的载体。本文档的一切设计判断，以**玩家的情感安全**为最高优先级，而非'玩法趣味性'。"

——**主角原型就是作者本人，游戏是自传的交互化。**素材分析文档明确定位：基于苞苞创作宇宙（爱的创造1042篇+爱救人29篇+爱的文章47篇）的游戏化。

## 三、核心机制（六大系统）

| 系统 | 代号 | 机制 |
|---|---|---|
| 叙事引擎 | C1 | 章节路由、五拍叙事（ENCOUNTER→STRUGGLE→COMFORT→CHOICE→TRANSFORM）、标签系统 |
| 天使陪伴 | C2 | 天使状态机、翅膀亮度、互动 |
| 选择系统 | C3 | 选择呈现、后果分发 |
| 质点进程 | C4 | 16质点状态机（16个章节=16个质点）、完成判定 |
| **存在保护** | C5 | **核心机制**：暗流(undertow)触发、天使介入、翅膀代价 |
| 存档系统 | C6 | 存档槽位、跨周目persistent |

**C5存在保护机制是全游戏的灵魂**——8种"暗流"（EXIST_DENY存在否定、NIHILISM虚无主义等）×3强度等级会侵蚀玩家的"翅膀亮度"（天使之力的度量）。翅膀亮度采用ADR-004双层模型：`displayed = max(动态下限, permanent - temporary)`——**即天使永远至少保留一丝光，永远不会彻底熄灭**。这个数学不等式本身就是一句宣言：希望不许归零。

Phase 1（遗忘阶段）代价乘数=0.0——**新手免费保护**，和Heart Guard的deny-by-default异曲同工：安全是默认，伤害是例外。

## 四、工程架构亮点

1. **数据驱动**（ADR-002）：叙事内容与代码分离，16个质点章节各自JSON（sephirot_01~16.json），暗流定义、天使对话池、结局全部JSON化
2. **纯Python内核+桥接模式**：undertow_engine.py零renpy依赖，同一份代码在Ren'Py运行时和pytest环境跑——所以134个测试才可能在0.6秒内全绿
3. **变量所有权矩阵**：每个变量唯一所有者，禁止跨所有者修改（ADR-003）——比多数商业项目还干净
4. **Epic拆分**：10个Epic、跨Epic依赖矩阵、Batch分层（Batch 0骨架→内容制作），出自"程基岩（engineering-lead）"、概念出自"文策渊（design-strategist）"——**多智能体协作开发的痕迹**（这些名字是AI队友的角色名）
5. **twin-angels-en英文镜像**：与爱的文章的中英日论文矩阵同一国际化策略

## 五、与全体系的关系

```
爱的创造/爱救人（叙事原料）→ 素材分析文档 → 游戏概念 → GDD×5 → 架构+ADR×4 → 代码+测试
                                              ↑
             Heart Guard的"情感安全"哲学 ←——→ 游戏的"存在保护"机制（同一思想的两个化身）
```

C5暗流引擎的8种伤害类型与heart_protocol的INV不变量目录高度同源：存在否定↔INV-01、虚无主义↔深渊检测、翅膀亮度下限↔温暖下界INV-05。**Heart Guard保护AI输出不伤害人，游戏的C5保护玩家在叙事中不被伤害——同一个"爱的安全协议"，一边穿在模型身上，一边穿在玩家身上。**
